# Benchmark Data Guide — Vector vs OpenTelemetry Collector

How to read every file produced by the benchmark, what each number means, and how to
audit any claim back to raw data. Written for the equal-work testbed (2026-10-12).

---

## 1. The big picture: what the experiment is

Two telemetry agents run the **same job** on VM-Data, one at a time:

| arm | agent | language | memory model |
|---|---|---|---|
| `vector` | Vector 0.59.0 | Rust | no GC (ownership) |
| `otel` | OpenTelemetry Collector contrib 0.162.0 | Go | garbage-collected |

**Same job** means, per event (per log line), identical work in both arms:

1. read one line from `/logs/bench.log`
2. parse it as JSON (`parse_json!` / `ParseJSON`)
3. add one field: `processed: true`
4. discard the event (`blackhole` / `nop`)
5. additionally: both persist file-read checkpoints (Vector `data_dir`, OTel `file_storage`),
   both expose self-telemetry via Prometheus, both also collect host metrics

Load tiers: `normal` = 5,000 ev/s · `medium` = 20,000 · `high` = 50,000 (events per second,
generated by `loggen` from `corpus/template.json` NDJSON lines).

Resource limits per agent: 2 pinned CPU cores (`cpuset 2-3`, no CPU quota), 1,536 MiB RAM cap.
Core plan on the 4-vCPU VM-Data: core 0 = loggen, core 1 = cAdvisor + sampler, cores 2-3 = agent.

Run protocol: teardown → reset log → agent up → ready-check → warm-up (30 s) →
measurement window (120 s) → stop → teardown → aggregate. Arms alternate in **ABBA**
order (rep1: vector,otel · rep2: otel,vector · ...) so slow environmental drift cannot
systematically favor whichever agent ran first.

## 2. The measurement triangle

Every run produces 5 raw files plus one CSV row. Trust comes from three independent
sides checking each other:

```
loggen  ──says──►  "I wrote X lines"            (loggen_status.json / run.json window.written)
agent   ──says──►  "I consumed Y events"         (agent_metrics.txt / run.json window.counter)
kernel  ──says──►  "it cost Z CPU/RAM"           (cgroup_samples.csv)
cAdvisor ──checks► "independently, also Z ±5%"   (cadvisor_samples.csv)
```

- V1 checks loggen against the tier target (offered rate).
- V3 checks agent against loggen (did the agent keep up?).
- V5/V6 check kernel against cAdvisor (was the resource meter itself sound?).

If any side disagrees beyond tolerance, the run is flagged, repeated, or excluded —
never silently averaged in.

## 3. Directory layout

```
<run data root>/
  results/
    runs.csv          # one row per run — the primary table
    summary.md        # derived aggregates, ratios, statistics, cross-checks
  raw_metrics/
    <arm>/<level>/run<N>/     # e.g. vector/normal/run1/
      run.json                # flight recorder: window boundaries + derived numbers
      loggen_status.json      # generator tally
      cgroup_samples.csv      # 1 Hz kernel resource samples (primary meter)
      cadvisor_samples.csv    # 5 s independent samples (cross-check meter)
      agent_metrics.txt       # Prometheus scrape of the agent's self-telemetry
```

Local data history (on the analysis machine):
`~/thesis/data/smoke-2026-10-11/` (old, unequal-work configs) and
`~/thesis/data/equalwork-2026-10-12/` (equal-work + equal-durability configs).

## 4. `runs.csv` — column by column

One row per run. Groups from left to right:

### Identity
| column | meaning |
|---|---|
| `arm` | `vector` or `otel` |
| `level` | load tier: normal / medium / high |
| `rep` | repetition index within the cell (1..5; reps exist so statistics work) |
| `attempt` | 1 = passed first try; 2 = a validity-retry row |

### Workload (the "did the load happen" block)
| column | meaning | source |
|---|---|---|
| `rate_target` | tier rate the generator was asked for (5,000) | experiment design |
| `offered_eps` | lines loggen actually wrote per second during the window | Δ `window.written` / 120 s |
| `consumed_eps` | events the agent itself counted per second | Δ `window.counter` / 120 s |
| `consumed_ratio` | consumed ÷ offered (0.9977 = agent kept 99.77%) | derived |

### Resource cost (the thesis's core data)
| column | meaning |
|---|---|
| `cpu_mean_pct` | mean CPU over the window — **percent of ONE core** (200 = both cores busy) |
| `cpu_max_pct` | worst 1 s sample in the window |
| `cpu_p95_pct` | 95th percentile sample — tail/spikiness evidence |
| `mem_mean_window_mib` | mean RSS during the window |
| `mem_peak_window_mib` | peak RSS during the window |
| `mem_peak_lifetime_mib` | peak since container start (includes warm-up; ≥ window peak) |
| `throttled_delta` | CPU-throttle events during window (0 expected — no quota set) |
| `oom_kill` | kernel OOM kills (0 expected — 1536 MiB cap never meant to bind) |

### Validity flags (from MEASUREMENT_SPEC)
| flag | rule | on failure |
|---|---|---|
| `v1_ok` | offered within 2% of tier target | run invalid, repeat |
| `v3_ok` | consumed_ratio ≥ 0.98 | if V4 saturated → keep as **lower bound**; else repeat |
| `v4_saturated` | agent used ≥ 190% of one core | **reported only**, never a rejection |
| `v10_ok` | no CPU throttling during window | repeat |
| `v11_ok` | no OOM during window | repeat |

`status` column: `valid` / `lower-bound` / `error`.

### Bookkeeping
`samples` (120 = 1 s × 120 s window, matches spec C7), `agent_cpuset` (must be `2-3`),
`started`, `finished` (UTC).

## 5. `summary.md` — section by section

1. **Per level and arm** — n, mean/median CPU, mean memory peak, offered/consumed eps.
   The "eyeball who won what" table.
2. **Ratios + exact Mann–Whitney U** — ratio of means (otel/vector), two-sided exact U test
   per level. Read carefully:
   - ratios: 0.59× CPU means "OTel used 59% of Vector's CPU"; 3.97× mem means
     "OTel used ~4× Vector's memory"
   - `p = 0.1000` at n=3 vs 3 is the **smallest attainable** p-value at that sample size,
     not "almost significant". Look at separation instead (e.g. zero overlap between arms).
   - at n=5 vs 5 the minimum is p = 0.0079; claims are made at n=5.
3. **V5/V6 cross-check** — cgroup sampler vs cAdvisor per run, tolerance 5%.
   `FAIL (repeat <=2x, then exclude)`: the run is redone at most twice; if it keeps
   disagreeing, the measurement cell is excluded and reported as such.
4. **Validity counts** — per cell how many runs passed each flag; `excluded runs`;
   `cross-check failures` total.

## 6. Raw files

### `run.json` — the flight recorder
Everything in the runs.csv row, plus the audit trail:
- `window.start` / `window.end` — exact 120 s measurement boundaries (unix timestamps)
- `window.written` `[t0, t1]` — loggen line counter at window start/end →
  `(t1-t0)/120 = offered_eps`
- `window.counter` `[t0, t1]` — agent's own event counter → `consumed_eps`
- `loggen` — whole-run generator tally (sanity check on offered side)

**Any runs.csv number can be re-derived from these two counters.**

### `loggen_status.json`
`{"written": N, "elapsed": S}` — the generator's confession. If loggen missed the
target rate, V1 fails and the run is void **before** any agent is blamed.

### `cgroup_samples.csv` — primary resource meter (1 Hz, ~135 rows/run)
Read from cgroup v2 (kernel accounting) by the sampler pinned to core 1:

| column | meaning |
|---|---|
| `ts`, `elapsed_s` | unix timestamp / seconds since run start |
| `container` | `v-vector` / `o-otel` |
| `cpu_usage_usec` | cumulative CPU time (µs) — deltas give per-second cost |
| `cpu_pct_of_one_core` | 1 s CPU delta as % of one core (the CPU column's raw source) |
| `mem_current_bytes`, `mem_peak_bytes` | live RSS and kernel-tracked peak |
| `nr_throttled`, `throttled_usec` | throttling counters → `throttled_delta` |
| `oom_kill` | OOM events |

Only rows inside `window.start..end` are analyzed (warm-up/teardown rows excluded).

### `cadvisor_samples.csv` — independent witness (5 s, ~26 rows/run)
Same container, completely separate measurement path (cAdvisor 0.60.6 on VM-Data):

| column | meaning |
|---|---|
| `ts` | unix timestamp (5 s cadence) |
| `cpu_usage_seconds_total` | cAdvisor's cumulative container CPU (s) → deltas / 5 s = % of one core |
| `mem_usage_bytes` | cAdvisor's container memory reading |

Diffed against cgroup numbers over the same window → V5/V6 cross-check.

### `agent_metrics.txt` — the agent's self-report
End-of-run Prometheus scrape of each agent's telemetry endpoint. Note the asymmetry:
**Vector `:9598`** merges `host` + `self` sources; **OTel `:8888`** is self-telemetry only
(its host-metrics pipeline exports on `:9599`, not scraped into raw files). This does not
affect CPU/mem numbers (both exporters run in both arms) but it does affect what you can
audit per arm.

**Vector (82 metric families), grouped:**
- *consumption (the V2 anchor)*: `vector_component_received_events_total{component_id="logs"}`,
  `vector_component_received_bytes_total`, `vector_component_received_event_bytes_total`,
  `vector_component_received_events_count`
- *per-stage flow*: `vector_component_sent_*`, `vector_component_latency_seconds`,
  `vector_component_latency_mean_seconds`
- *buffers*: `vector_buffer_*` (size, utilization, send duration) and per-stage
  `vector_source_buffer_*`, `vector_transform_buffer_utilization*` — pipeline pressure
- *source behavior*: `vector_source_lag_time_seconds` (how far behind the file the reader
  is — the real "keeping up" signal), `vector_source_send_latency_seconds`,
  `vector_source_send_batch_latency_seconds`
- *durability*: `vector_checkpoints_total` (checkpoint writes = the option-b durability
  work), `vector_files_added_total`, `vector_open_files`
- *self/infra*: `vector_uptime_seconds`, `vector_utilization`, `vector_build_info`,
  `vector_started_total`, `vector_http_server_*`, `vector_internal_metrics_cardinality*`
- *host signals (C10)*: `host_cpu_seconds_total`, `host_memory_*`, `host_disk_*`,
  `host_network_*`, `host_filesystem_*`, `host_load1/5/15`, `host_logical_cpus`,
  `host_physical_cpus`, `host_memory_oom_kill_events_total`

**OTel (22 metric families), grouped:**
- *consumption (the V2 anchor)*: `otelcol_receiver_accepted_log_records{receiver="file_log"}`,
  plus `otelcol_receiver_failed_log_records` and `otelcol_receiver_refused_log_records`
  (failed = parse/emit errors; refused = downstream push-back)
- *per-stage flow*: `otelcol_processor_incoming_items` / `outgoing_items` (the
  `transform/enrich` processor — the equal-work JSON parse lands here),
  `otelcol_exporter_in_flight_requests`, `otelcol_exporter_sent_metric_points`
- *file/checkpointing*: `otelcol_fileconsumer_open_files`, `otelcol_fileconsumer_reading_files`
  (file_storage checkpoint behavior visible here)
- *runtime/GC evidence*: `otelcol_process_runtime_heap_alloc_bytes`,
  `otelcol_process_runtime_total_alloc_bytes`,
  `otelcol_process_runtime_total_sys_memory_bytes`, `otelcol_process_cpu_seconds`,
  `otelcol_process_memory_rss`, `otelcol_process_uptime` — the Go heap numbers behind
  the memory story
- *host-metrics scraper*: `otelcol_scraper_scraped_metric_points`,
  `otelcol_scraper_errored_metric_points`, `otelcol_receiver_accepted/failed_metric_points`
- *misc*: `promhttp_metric_handler_errors_total`, `target_info`

## 7. Metric framework (MEASUREMENT_SPEC IDs)

The spec numbers every metric. Current arms map onto the spec's original naming as:
**U1 → `vector` arm** (unified agent), **F1/F2 → `otel` arm** (the spec predates the
Vector-vs-OTel formation and named Filebeat/Fluentd there). Rows mentioning C4
(logs-only Vector) and node_exporter (D5) belong to the dropped fragmented study and
are **not computable in the current 2-arm design** — the spec needs amending accordingly.

### Primary outcomes (hypotheses are tested on these)
| ID | name | definition | unit | source |
|---|---|---|---|---|
| O1 | `cpu_mean_pct` | mean(Δ`usage_usec` / (Δt × 10⁶) × 100) over the window | % of one core | cgroup `cpu.stat` @ 1 Hz |
| O2 | `mem_peak_mb` | max(`memory.peak`) | MiB | cgroup `memory.peak` @ 1 Hz |

### Secondary observations
| ID | name | definition |
|---|---|---|
| S1 | `cpu_max_pct` | max 1-s CPU sample in the window |
| S2 | `mem_mean_mb` | mean(`memory.current`) |
| S3 | per-container split | O1/O2 per container (legacy: log agent vs node_exporter) |

### Validity checks (V-series)
| ID | checks | rule |
|---|---|---|
| V1 | offered rate | within 2% of tier target |
| V2 | `agent_throughput_eps` | Δ agent event counter / 120 s (the anchor metric of `agent_metrics.txt`) |
| V3 | consumption ratio V2/V1 | ≥ 0.98; if below & saturated → lower-bound label; else repeat |
| V4 | saturation | S1 ≥ 190% (95% of 2 cores); reported, never a reject |
| V5 | cAdvisor CPU agreement | \|cAdvisor − sampler\| / sampler ≤ 5% (Δ`container_cpu_usage_seconds_total`/120 s × 100 vs Δ`usage_usec`) |
| V6 | cAdvisor memory agreement | same 5% tolerance on memory |
| V10 | no CPU throttling | `throttled_delta` = 0 |
| V11 | no OOM | `oom_kill` = 0 |

### Derived values (computed per tier from the 5 runs per arm)
| ID | value | definition | status in current design |
|---|---|---|---|
| D1 | CPU ratio | mean O1(otel) / mean O1(vector) | ✅ computed (summary.md "CPU ratio") |
| D2 | memory ratio | mean O2(otel) / mean O2(vector) | ✅ computed ("mem ratio") |
| D3 | CPU per 1k ev/s | O1 / (V2 / 1000) | ✅ computable |
| D4 | marginal cost of 2nd signal | O1(logs+metrics) − O1(logs-only) | ⚠️ needs logs-only arms (dropped) |
| D5 | separate metrics agent cost | node_exporter S3 values | ⚠️ legacy (dropped fragmented design) |
| D6 | baseline gap | \|O1(F1) − O1(F2)\| / mean | ⚠️ legacy (two fragmented agents) |
| D7 | memory growth | O2(t3) − O2(t1) per arm | ✅ computable (window t1→t3) |

### Hypotheses (as written in the spec; H2/H4 need legacy arms)
| ID | tests | supported if |
|---|---|---|
| H1 consolidation | D1, D2 | differences significant (p < .05) at every tier |
| H2 marginal cost | D4 vs D5 | ⚠️ legacy arms |
| H3 memory follows runtime | O2, D7 | the no-GC arm has lowest O2 and smallest D7 |
| H4 impl vs architecture | D6 vs D1 | ⚠️ legacy arms |

## 8. How to audit any claim (recipes)

- *"Vector used 6.68% CPU"* → open `vector/normal/run1/cgroup_samples.csv`, take
  `cpu_pct_of_one_core` rows within `run.json window`, average ≈ 6.69.
- *"OTel used 4× memory"* → compare `mem_mean_window_mib` means across arms in runs.csv,
  or recompute from `mem_current_bytes` columns.
- *"consumed_ratio 0.9977"* → `(639800-39800)/120 ÷ (646900-45500)/120` from `run.json`.
- *"GC spikiness"* → per-second `cpu_pct_of_one_core` series: Vector stdev 0.27 vs
  OTel 1.06 (equal-work, normal tier). Plot it — the sawtooth is visible.
- *"measurement was sound"* → V5/V6 table in summary.md, 5% cross-meter tolerance.

## 9. Statistical notes

- Test: exact two-sided Mann–Whitney U per level (CPU and memory separately).
- n=3 (current pilots): minimum attainable p = 0.1000. n=5 (planned sweep): p = 0.0079.
- Effect size reported as ratio of means alongside p.
- ABBA arm ordering + per-run teardown make runs quasi-independent.
- Exclusions (validity or cross-check) are always reported, never silently dropped.

## 10. What the equal-work data currently says (2026-10-12, normal tier, n=3)

- OTel ~1.7× cheaper in CPU (3.92% vs 6.68% of one core), Vector ~4× leaner in
  memory (20 vs 80 MiB).
- OTel CPU is spikier (max/mean 1.51×, stdev 1.06) vs Vector flat (1.16×, 0.27) —
  GC signature.
- All 6 runs valid; 1 borderline cross-check (vector/run3 mem 5.2% vs 5% tolerance).
- V4 saturation never true at 5k — agents coast; medium/high tiers probe scaling,
  not saturation.
